           Tree-based Chained Hash Integrity Coding for HTTP
                 draft-meunier-httpbis-tree-chic-latest

Abstract

   This document describes a content-coding for HTTP that supports
   progressive integrity verification and verification of selected
   ranges.

1.  Introduction

   [CHIC] splits content into chunks.  Each non-final chunk carries the
   hash of the next.  A recipient that starts with the first hash
   follows this chain to verify the content.  Verifying a later chunk
   requires reading the earlier chunks.

   This document replaces the chain with a Merkle tree.  A trusted root
   hash and a proof allow a recipient to verify a chunk without reading
   earlier content.  Chunks can be read sequentially, by range, or out
   of order.

   The sender computes the tree in advance and stores it with the
   content.  The server serves byte ranges of this encoded
   representation without constructing proofs for individual requests.

2.  Example

   A client wants one article from a Wikipedia archive.  The archive
   consists of independently compressed streams, with an index that
   locates the stream containing each article.  The client has a trusted
   root hash for the archive encoded with the tree-chi content coding.

   In this example, the encoded representation is 1,004,096 bytes long.
   Its length prefix and tree occupy the first 4,096 bytes.  The
   compressed archive follows unchanged.  These sizes are illustrative.

   The client first requests the beginning of the encoded
   representation:

   GET /wikipedia.xml.bz2 HTTP/1.1
   Host: example.com
   Accept-Encoding: tree-chi
   Range: bytes=0-4095

   HTTP/1.1 206 Partial Content
   Content-Type: application/octet-stream
   Content-Encoding: tree-chi
   Content-Range: bytes 0-4095/1004096
   Content-Length: 4096
   ETag: "wiki-tree-1"
   Vary: Accept-Encoding

   [4096 bytes containing the length prefix and tree]

   The client verifies the tree against its trusted root.  The article
   index locates a compressed stream at archive offsets 65,536 through
   98,303.  That stream is also one chunk of the coding.  The verified
   tree establishes its position, length, and expected hash.

   Byte ranges address the encoded representation (Section 14.1.2 of
   [HTTP]).  Adding the 4,096-byte prefix gives the range 69,632 through
   102,399:

   GET /wikipedia.xml.bz2 HTTP/1.1
   Host: example.com
   Accept-Encoding: tree-chi
   If-Match: "wiki-tree-1"
   Range: bytes=69632-102399

   HTTP/1.1 206 Partial Content
   Content-Type: application/octet-stream
   Content-Encoding: tree-chi
   Content-Range: bytes 69632-102399/1004096
   Content-Length: 32768
   ETag: "wiki-tree-1"
   Vary: Accept-Encoding

   [32768 bytes containing the compressed stream]

   Using the retained tree, the client verifies the chunk, decompresses
   the stream, and extracts the article.  This retrieves 36,864 bytes of
   the encoded representation.  The compressed stream can contain other
   articles, but the client does not need the rest of the archive.

   The If-Match header field (Section 13.1.1 of [HTTP]) makes the second
   request conditional on the same representation.  The trusted root
   provides the integrity check.

   For a larger tree, the client could retrieve only the records needed
   for the selected chunks.  A full response carries the tree followed
   by the archive, allowing the client to verify chunks as they arrive.

2.1.  Comparison with CHIC

   Both codings require a particular encoded representation.  Starting
   with only the initial hash, CHIC requires the preceding chunks to
   verify a selected range.  Tree CHIC uses tree records to verify that
   range without retrieving the preceding content.

3.  Format Overview

   Chunks can have different lengths.  Branches commit to the lengths
   and hashes of their children.  This lets a reader verify a chunk and
   its position in the content.  As with [CHIC], construction requires
   the complete content.

   Lengths and hashes sit in a tree header before the content.  The
   content bytes stay contiguous, with no framing between chunks.  A
   header length allows a reader to skip the tree and locate the
   content.

   The tree header contains records of this form (tags omitted):

                              Root hash
                                  ^
                                 Hash
                                  |
                    +---------------+---------------+
                    | Len L, Hash L | Len R, Hash R |
                    +---------------+---------------+
                          /               \
                        Hash              Hash
                         |                 |
             +----------+----------+ +----------+----------+
             | Len 0,H0 | Len 1,H1 | | Len 2,H2 | Len 3,H3 |
             +----------+----------+ +----------+----------+
                   |           |           |           |
                  Hash        Hash        Hash        Hash
                   |           |           |           |
                Chunk 0     Chunk 1     Chunk 2     Chunk 3

                 Figure 1: Tree Header (Logical Structure)

   On the wire:

     +------------+----------------+----~~~~----+----~~~~----+
     | Header Len | Tree Header    |  Chunk 0   |  Chunk 1 ...|
     +------------+----------------+----~~~~----+----~~~~----+
     <-- First byte                              Last byte -->
                                   <-- Continuous content -->

                        Figure 2: Overview of Format

   *  Header length counts tree header bytes, excluding the length field
      itself.

   *  Length beside a hash counts content bytes covered by that hash.

   *  A sequential reader receives the tree header before the first
      chunk.

5.  Chained Hash Integrity Format

5.1.  Format Description

   *  Encoding: header length, tree header, original content bytes.

   *  Tree header: branch records with a content length beside each
      child hash.

   *  Leaf hashes cover chunks in the continuous content region.

   *  Branch hashes commit to child lengths as well as child hashes.

   *  Root hash carried outside the content.

5.2.  Consumption and Validation

   Read the header length and parse the tree header.  Start with a
   trusted root hash.  Verify branches before trusting their child
   hashes and content lengths.  Use the lengths to split the content
   into chunks.  Verify each chunk before releasing it.

   For a range, retrieve the covering chunks and the required header
   records.  Content offsets are sums of preceding chunk lengths.
   Stored offsets add the length field size and tree header length.

5.3.  Construction

6.3.  Compression

   Content-Encoding can list multiple codings in the order they were
   applied (Section 8.4 of [HTTP]).  For example, Content-Encoding:
   gzip, tree-chi applies gzip first, then this coding.  The recipient
   verifies the compressed chunks while removing the tree coding, then
   decompresses them.

   The order Content-Encoding: tree-chi, gzip compresses the tree and
   content together.  The recipient decompresses before verifying.  Byte
   ranges then address that outer compressed representation, so the
   offsets in Section 2 would no longer apply.

   Neither order makes a gzip stream independently decompressible at
   arbitrary offsets.  The archive in Section 2 already has
   independently compressed streams.  A client can decompress a selected
   stream after verifying its bytes.  This compression is part of the
   archive format.
