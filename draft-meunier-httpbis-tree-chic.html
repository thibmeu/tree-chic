Tree-based Chained Hash Integrity Coding for HTTP

Abstract

This describes a content-coding for HTTP that enables progressive processing of content, with ranges, without sacrificing integrity.¶

1. Introduction

[CHIC] splits content into chunks. Each non-final chunk carries the hash of the next. Verification follows the chain from the first chunk. Starting from its hash, reading a later range requires verifying the preceding chunks.¶

This document replaces the chain with a Merkle tree. A trusted root hash and a proof allow a recipient to verify a chunk without reading earlier content. Chunks can be read sequentially, by range, or out of order.¶

  • Variable-length chunks, as in [CHIC]. Boundaries can follow application needs, such as progressive image rendering.¶

  • Subtree content lengths authenticate chunk positions in the byte stream.¶

  • Precompute and store the tree with the content. Serve both from ordinary object storage, such as S3, using range requests. No server-generated proofs.¶

  • Share proof hashes across chunks. TODO: overhead and verifier state.¶

  • Finish the content before publishing the root hash, as with CHIC.¶

Lengths and hashes sit in a tree header before the content. The content bytes stay contiguous, with no framing between chunks. A header length allows a reader to skip the tree and locate the content.¶

3. Chained Hash Integrity Format

3.1. Format Description

  • Encoding: header length, tree header, original content bytes.¶

  • Tree header: branch records with a content length beside each child hash.¶

  • Leaf hashes cover chunks in the continuous content region.¶

  • Branch hashes commit to child lengths as well as child hashes.¶

  • Root hash carried outside the content.¶

3.2. Consumption and Validation

Read the header length and parse the tree header. Start with a trusted root hash; verify branches before trusting their child hashes and content lengths. Use the lengths to split the content into chunks. Verify each chunk before releasing it.¶

For a range, retrieve the covering chunks and the required header records. Content offsets are sums of preceding chunk lengths. Stored offsets add the length field size and tree header length.¶

3.3. Construction

Split content into chunks. Hash leaves, then branches, up to the root. Chunks can be hashed independently. Write the header length and tree header, then copy the original content unchanged.¶

4.3. Example

Full response, following the header layout in [CHIC]. Angle-bracket values are placeholders, not valid wire syntax.¶

HTTP/1.1 200 OK
Content-Type: application/octet-stream
Content-Encoding: tree-chi
Content-Length: <encoded length>
Content-Digest: tree-chi=:<base64 root hash>:
Accept-Ranges: bytes
¶

Range retrieval from the stored encoding:¶

GET /object HTTP/1.1
Host: example.com
Range: bytes=<start>-<end>
¶ 
HTTP/1.1 206 Partial Content
Content-Type: application/octet-stream
Content-Encoding: tree-chi
Content-Range: bytes <start>-<end>/<encoded length>
Content-Length: <range length>
¶

The recipient already holds the trusted root. Additional ranges may be needed for tree header records. These offsets address the stored encoding, including the length prefix and tree header.¶
